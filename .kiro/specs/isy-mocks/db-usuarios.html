Política de sesión y tokens (access vs refresh)

El access token NO se guarda en la base. Es de vida corta y stateless (JWT firmado): el backend lo valida por firma, sin tocar la BD. Por eso user_sessions guarda solo el hash del refresh token — y así debe ser.

TokenVigencia típicaDónde se guarda (cliente)Qué guarda el servidor
Access token15–60 minmemoria (o secure storage)nada (se valida por firma)
Refresh token30–60 días deslizante + tope absolutosecure storage del SO (Keychain/Keystore)solo el hash en user_sessions

Ciclo de vida

  1. Login/registro → emite access + refresh; guarda el hash del refresh en user_sessions.
  2. El access caduca → el cliente refresca con su refresh token → nuevo par (refresco silencioso).
  3. Rotación: cada refresco reemplaza refresh_token_hash y actualiza last_used_at (vigencia deslizante). Reusar uno viejo = posible robo → revoked_at.
  4. Cerrar sesión / revocar (todos los dispositivos, cambio de contraseña) → revoked_at.

El access token se "mata" dejándolo caducar (por eso es corto). Para revocación inmediata se usaría una lista de bloqueo por jti, pero nunca se almacena el token completo.
